# Архитектура

## Сохранения

Данные игрока — `PlayerData` (`Runtime/Infrastructure/Data`). Сервисы читают и пишут свою часть через `IDataReader<PlayerData>` / `IDataWriter<PlayerData>`, регистрируясь в `PlayerDataProvider`. Сериализация — Newtonsoft.Json (`Core/DataManagement/Serializers/JsonSerializer.cs`).

### Совместимость со старыми сохранениями

Файл, сохранённый старой версией игры, может не содержать новых полей или новых ключей. Это решается в двух местах:

1. **Значение по умолчанию — в объявлении поля `PlayerData`.** Newtonsoft создаёт объект конструктором и заполняет только те поля, что есть в JSON; отсутствующие сохраняют значение из объявления.
2. **Недостающие ключи словарей — в `PlayerDataProvider.FillMissingData`.** После загрузки `DataProvider.LoadAsync` передаёт туда загруженные данные и стартовые (`GetOriginData()`, те же, что для новой игры). `AddMissingKeys` добавляет только отсутствующие ключи, сохранённые значения не трогает.

Что делать при добавлении данных:

| Что добавляешь | Что делать |
|---|---|
| Новое значение в существующий enum (валюта, стат) | Ничего — `AddMissingKeys` подтянет ключ из стартовых данных |
| Новый словарь, где у каждого ключа есть стартовое значение | Поле с `= new()` + строка `AddMissingKeys(loadedData.X, originData.X)` в `FillMissingData` + заполнение в `GetOriginData` |
| Новая коллекция, пустая на старте | Только `= new()` в объявлении поля |
| Новое число или флаг с нестандартным стартом | Значение прямо в объявлении: `public int Energy = 5;` — не через `FillMissingData`: после загрузки не отличить «поля не было» от «сохранён 0» |

Тест `PlayerDataProviderTests.Deserialize_EmptyJson_HasNoNullFields` проверяет, что ни одно ссылочное поле `PlayerData` не остаётся `null` после загрузки пустого `{}` — ловит поле, объявленное без `= new()`.

**Ограничение: список с непустым стартовым значением** (например, «на старте открыт герой 1»). Писать `= new() { 1 }` нельзя: Newtonsoft по умолчанию (`ObjectCreationHandling.Auto`) дописывает элементы из файла в существующий список, и сохранённое `[1, 2]` загрузится как `[1, 1, 2]`. Когда такой список понадобится — включить `ObjectCreationHandling.Replace` в `JsonSerializer` (коллекция из файла заменяет значение из объявления; если поля в файле нет — остаётся стартовое).

**Когда вводить версию сохранения и миграции:** при ломающих изменениях формата — переименование или перенос поля, смена смысла значения. Дополнение недостающих данных этого не требует.

## Статы героя и модификаторы

Компоненты сущности (`Gameplay/Features/StatsFeature`):

- `BaseStats` — значения из прокачки (`StatsUpgradeService`), в бою не меняются;
- `StatsEffects` — список модификаторов `IStatsEffect` (`StatsEffect`: стат + функция `float → float`);
- `ModifiesStats` — итоговые значения, их читают системы-синхронизаторы (`…StatSynchronizerSystem`) и переносят в `Damage`, `MaxHealth` и т. д.

`StatEffectsApplierSystem` при каждом добавлении или удалении эффекта пересчитывает итог с нуля: копирует `BaseStats` в `ModifiesStats` и по очереди применяет все эффекты.

**Правило: стат в бою меняется только добавлением эффекта в `StatsEffects`.** Прямая запись в `ModifiesStats` стирается при следующем пересчёте. Так терялся купленный буст урона (`IncreaseDamageAbilitySystem`) после подбора любой способности на статы — исправлено, покрыто тестом `StatEffectsApplierTests.AddEffect_AfterIncreaseDamageBoost_KeepsBoost`.

**Порядок эффектов влияет на итог.** Эффекты применяются в порядке добавления: `+5`, затем `×2` даёт `(10 + 5) × 2 = 30`, в обратном порядке — `10 × 2 + 5 = 25`. Сейчас все способности на урон — умножение (от порядка не зависит). Если появятся сложения вместе с умножениями и порядок станет проблемой — применять эффекты по фиксированным стадиям (сначала сложение, потом умножение).

**Какие статы есть у героя, решает `PlayerStatsUpgradeConfig`.** `StatsUpgradeService.ReadFrom` пропускает статы, которых нет в конфиге, а `MainHeroFactory` собирает `BaseStats` только из `AvailableStats`. Поэтому стат можно убрать из игры, оставив значение в enum и в старых сохранениях. Удалить значение из enum можно, только если его нет ни в одном сохранении: Newtonsoft не загрузит словарь с неизвестным ключом. Так 05.11.2026 удалён `AttackRadius` (его заменила дальность `AttackRange`): игра ещё не выпущена, ключ убран из единственного сохранения в редакторе.

**Скорость атаки** (`AttacksPerSecond`) меняет не одно время, а все три: `AttackTimeByAttackSpeedStatSynchronizerSystem` пересчитывает `AttackProcessModifiedTime`, `AttackDelayModifiedTime` и `AttackCooldownModifiedTime` из исходных, а таймеры атаки читают Modified-значения. Скорость анимации подгоняет `InstantAttackAnimationSpeedView` (множитель Initial / Modified).

**Как добавить новый стат:**

1. значение в `StatTypes` (не менять числа существующих — по ним стоят ассеты);
2. строка в `PlayerStatsUpgradeConfig` (уровни прокачки и цена);
3. строка в `StatsViewConfig` (название и иконка в окне прокачки);
4. синхронизатор `…StatSynchronizerSystem`, переносящий `ModifiesStats` в компонент, который читает игровая система, и его подключение в `EntitiesFactory.CreateHeroEntity`;
5. при желании — способности `IncreaseStat` на этот стат (ассет + запись в `AbilitiesConfigsContainer`).

## Реактивность

Своя реализация (`Core/Reactive`): `ReactiveVariable<T>` (уведомляет `(старое, новое)` при изменении `Value`), `ReactiveEvent<T>` / `ReactiveEvent`. Подписчики хранятся в общем `SubscribersList<T>`.

- Подписка и отписка внутри обработчика применяются со следующего уведомления (как у C# `event`): они ставятся в очередь, очередь разбирает только самый внешний вызов.
- **Вложенный вызов безопасен.** Обработчик может снова изменить ту же переменную или вызвать то же событие (так делает `LevelUpSystem`: в обработчике опыта записывает остаток обратно в опыт). Раньше это падало с `Collection was modified`, если в этот момент кто-то подписывался или отписывался; исправлено счётчиком вложенности, покрыто тестами `…FromHandlerWhileSubscriptionPending_DoesNotThrow`.
- **Правило для подписчиков:** при вложенных изменениях уведомления приходят не по порядку (сначала вложенное `120 → 20`, потом внешнее `0 → 120`). Если переменную могут менять из обработчиков, читай текущее `Value`, а не аргумент `newValue` (так делает `MainHeroExperiencePresenter`).
- `Subscribe` не присылает текущее значение (в отличие от `ReactiveProperty` в R3) — начальное состояние читать через `Value` при подписке.

## DI: VContainer (ADR)

**Статус:** принято, 26.10.2026.

**Контекст.** Был самописный контейнер (`Core/DI`): регистрация фабричными методами, дочерний контейнер на сцену, `IInitializable`/`IDisposable`. Фабрики и презентеры получали сам контейнер и вызывали `Resolve` внутри (service locator: 205 вызовов в 20 файлах). При разборе нашлись баги жизненного цикла:

1. Ленивый сервис, впервые запрошенный после `Initialize()`, не получал `IInitializable.Initialize()`.
2. `Initialize()` проходил по регистрациям один раз: если `NonLazy`-сервис при создании запрашивал ленивый, стоящий раньше в списке, тот создавался после прохода и тоже не инициализировался.

**Решение.** Перейти на VContainer 1.19.0.

1. Сначала убрать service locator на старом контейнере: зависимости — через конструктор, контейнер видит только корень композиции (`*ScopeInstaller`, `*Bootstrap`, `GameEntryPoint`). После этого замена контейнера свелась к регистрациям.
2. Области создаются **из кода**: корневая — `LifetimeScope.Create` в `GameEntryPoint` (`DontDestroyOnLoad`), сцены — `CreateChild` в `SceneSwitcherService`. Сцены и префабы не меняются.
3. Регистрации — автосвязывание (`builder.Register<T>(Lifetime.Singleton)`); лямбды — только для конфигов (читаются при первом запросе, после загрузки), префабов (`Instantiate`) и аргументов сцены (`RegisterInstance`).
4. Сервисы с `Initialize` — точки входа (`RegisterEntryPoint().AsSelf()`): VContainer создаёт их при построении области и вызывает `Initialize` по порядку регистрации. VContainer вызывает `Initialize` **только у точек входа** — сервис с `IInitializable`, зарегистрированный обычным `Register`, его не получит.
5. Сервисы, которые должны существовать до загрузки сохранения (сами регистрируются в `PlayerDataProvider` в конструкторе), создаются заранее через `RegisterBuildCallback`.

**Альтернативы.**

- *Zenject (Extenject)* — тот же функционал, но проект не развивается с 2022 года, медленнее, больше аллокаций, огромный API.
- *Починить свой контейнер* — два найденных бага чинятся, но это поддержка велосипеда без выигрыша; диагностика, производительность и знакомость для команды — у готового решения.
- *Области через компонент `LifetimeScope` на сцене* — стандартный способ, но требует правки сцен и смены схемы загрузки; создание из кода сохранило существующий поток `SceneSwitcherService`.

**Последствия.**

- Зависимости видны в конструкторах; классы создаются в тестах без контейнера. Большие конструкторы (`GameplayStatesFactory` — 17 параметров) стали заметны; фабрику состояний решили не делить — см. «Фабрика состояний без контейнера (ADR)».
- `LifetimeScope` — `MonoBehaviour` и освобождает сервисы в `OnDestroy`. При выходе из игры Unity уничтожает объекты в произвольном порядке, поэтому `SceneSwitcherService` освобождает область сцены на `Application.quitting`, пока все объекты живы.
- Освобождение области вызывает `Dispose` у всех созданных `IDisposable`: сервисы, меняющие глобальное состояние, обязаны вернуть его в `Dispose` (пример — `TimeScalePauseService` снимает паузу).
- **Риск для WebGL/IL2CPP:** VContainer создаёт объекты через рефлексию по конструкторам; агрессивное вырезание кода (managed stripping) может удалить «неиспользуемые» конструкторы. Проверить на WebGL-сборке; решение — `link.xml` или source generator VContainer.
- Известная временная связность, оставленная как есть: сервисы-читатели сохранения регистрируются в `PlayerDataProvider` в своём конструкторе (отсюда `RegisterBuildCallback`).

**Ревью по документации VContainer (05.11.2026).** Конструкторное внедрение, области из кода с `CreateChild` и явным `Dispose`, `RegisterEntryPoint`, `RegisterBuildCallback` для раннего создания — так, как описано в документации.

- **Игровой цикл — точка входа `GameplayLoop` (`ITickable`, `ILateTickable`)** вместо `Update`/`LateUpdate` в `GameplayBootstrap`, который вручную доставал сервисы из контейнера. Документация советует побочные эффекты держать в точках входа, а ручной `Resolve` — только когда другие способы не подходят. Один класс-цикл, а не `ITickable` у каждого сервиса: VContainer вызывает их в порядке регистрации, а порядок «мозги → сущности → состояния» важен для логики — в `GameplayLoop` он записан явно, и сервисы не зависят от фреймворка. Бутстрап только создаёт героя и башню и запускает машину состояний.
- **Регистрации — установщики `IInstaller`** (`ProjectScopeInstaller`, `MainMenuScopeInstaller`, `GameplayScopeInstaller`) вместо статических `*ContextRegistrations.Configure`: «Context» — словарь Zenject, в VContainer это «scope» и «installer». Аргументы области (`LaunchSettings`, `GameplayInputArgs`) — в конструкторе установщика; `SceneBootstrap.CreateInstaller(args)` отдаёт установщик, `SceneSwitcherService` передаёт его в `CreateChild(installer, name)`. Делегат `CreateSceneSwitcherService` заменён на `Register<SceneSwitcherService>(...).WithParameter("emptySceneName", Scenes.Empty)`.
- **Source generator / `link.xml` не ставим заранее**: делаем, если в WebGL/IL2CPP-сборке появятся ошибки создания объектов (решение пользователя).
- **`IPresenter` наследует `IInitializable` из `VContainer.Unity`** (UI зависит от интерфейса DI) — оставлено как есть, чтобы не трогать работающие окна (решение пользователя).

## Асинхронность: UniTask (ADR)

**Статус:** принято, 27.10.2026.

**Контекст.** Вся асинхронность была на корутинах: загрузка конфигов, сохранения, смена сцен, анимации попапов, таймер, очередь окон выбора способности. Корутины запускал общий `CoroutinesPerformer` (`MonoBehaviour` с `DontDestroyOnLoad`), который передавали в конструкторы почти двадцати классов. Проблемы:

1. Результат возвращался через колбэк (`Load<T>(Action<T> onLoad)`, `Exists(Action<bool>)`), а ветвление по нему требовало локальной переменной снаружи корутины.
2. Корутины не останавливались вместе с владельцем. `DropAbilityOnMainHeroLevelUpService` жил в области сцены, а его корутина — на `CoroutinesPerformer`, и после выхода из уровня она продолжала висеть.
3. Ошибка внутри корутины молча обрывала её (так в старой сборке зависал экран загрузки).
4. Тестам нужен был самописный `CoroutineRunner`, который прокручивал `IEnumerator` с вложенными `yield return`.

**Решение.** Перейти на UniTask 2.5.11 (git URL с тегом) и убрать `CoroutinesPerformer`.

1. Методы возвращают `UniTask` / `UniTask<T>` и называются `...Async`. Результат — возвращаемое значение, а не колбэк: `if (await provider.ExistsAsync())`.
2. «Запустить и не ждать» — `.Forget()` (сохранение после победы, переход между сценами по кнопке). Исключения из `Forget` UniTask пишет в лог, а не теряет.
3. **Отмена — у владельца процесса.** Класс, запускающий долгий процесс, держит свой `CancellationTokenSource` и отменяет его в `Dispose`: `TimerService`, `PopupPresenterBase`, `DropAbilityOnMainHeroLevelUpService`. `Dispose` вызывает тот, кто владеет объектом: область VContainer, `PopupService`, машина состояний. Отменённая задача выходит через `OperationCanceledException`, которое `Forget` молча гасит.
4. Анимации попапов (DOTween) ожидаются через `tween.ToUniTask(TweenCancelBehaviour.CancelAwait, token)`: отмена прекращает ожидание, но не трогает твин — как раньше `StopCoroutine`. DOTween лежит в `Assets`, а не пакетом, поэтому интеграцию включает define `UNITASK_DOTWEEN_SUPPORT` (Standalone, WebGL, Android).
5. Конфиги грузятся по-настоящему асинхронно (`Resources.LoadAsync`), а не `Resources.Load` с `yield return null` между файлами.
6. Сохранения (`LocalFileDataRepository`) остаются синхронными внутри и возвращают завершённую задачу: файлы маленькие, а на WebGL нет потоков. Интерфейс уже асинхронный, поэтому переход на облачные сохранения не потребует менять вызывающий код.

**Альтернативы.**

- *Оставить корутины* — работают, но не дают результат без колбэков, отмену по владельцу и нормальную обработку ошибок.
- *`Awaitable` (встроен в Unity 6)* — без зависимостей, но нет `WhenAll`/`WhenAny`, нет интеграции с DOTween, `Awaitable` нельзя ждать дважды (объекты переиспользуются из пула), и экосистема меньше.
- *`Task` из .NET* — аллокации на каждый вызов, продолжения через `SynchronizationContext`, на WebGL нет потоков.

**Последствия.**

- `ICoroutinesPerformer` исчез из конструкторов (≈20 классов); `CoroutineRunner` в тестах не нужен, тесты — `async Task` с `await`.
- В Unity 2023.1+ UniTask не добавляет `GetAwaiter` для `AsyncOperation` (конфликт со встроенным `Awaitable`), поэтому загрузка сцен и ресурсов вызывает `.ToUniTask()` явно.
- `GameEntryPoint.InitializeAsync` запускается без токена: объект точки входа уничтожается при смене сцены, а инициализация должна продолжиться.
- Сохранение не отменяется при выходе из сцены — данные должны записаться.

## Окна: открытие через `await` (ADR)

**Статус:** принято, 27.10.2026.

**Контекст.** `PopupService.Open...Popup()` возвращал презентер сразу, а о закрытии сообщал колбэк `closedCallback`. Проблемы:

1. Окна сами решали, что делать дальше: поражение, победа и плитка уровня вызывали `SceneSwitcherService`, окно способности само выдавало способность. UI знал про сцены и игровую логику.
2. Ждать окно приходилось флагом и опросом: колбэк обнулял поле, `UniTask.WaitUntil` каждый кадр проверял его (`DropAbilityOnMainHeroLevelUpService`).
3. Результат (какую кнопку нажали, что выбрали) до вызывающего кода не доходил.

**Решение.** Открытие окна — `UniTask`, который завершается, когда окно закрылось (анимация скрытия доиграла, презентер и view освобождены).

1. **Окно только показывает и спрашивает, решает тот, кто открыл.** Результат — свойство окна, его возвращает метод `Open...Async`: поражение — `DefeatPopupResult` (`Continue` / `Restart`), способность — `AbilityDropOption`, уровни — `int?` (`null` — закрыли крестиком). Переход делает вызывающий код: `DefeatState`, `WinState`, `MainMenuScreenPresenter`; способность выдаёт `DropAbilityOnMainHeroLevelUpService`.
2. **Один путь закрытия.** Кнопка, крестик и отмена ведут в `PopupService.ClosePopup`: анимация → освобождение → `UniTaskCompletionSource.TrySetResult()`. Повторное закрытие игнорируется (`IsClosing`).
3. **Чем закрывать окно:**

   | Причина | Как |
   |---|---|
   | Игрок сделал выбор | результат окна |
   | Закончилось время жизни того, кто открыл (вышли из состояния) | токен отмены владельца: `PreparationState` (окно построек), `WinState` / `DefeatState` |
   | Ушли со сцены | `PopupService.Dispose` → `TrySetCanceled()` всем открытым окнам, ожидающий код не висит |

   Отмена — исключение (`OperationCanceledException`), поэтому для обычного исхода логики её не используем: обычный исход — это результат. Где окно живёт столько же, сколько сцена (меню), токен не передаётся — хватает `Dispose`.
4. Подписка на закрытие — до `Initialize`, поэтому окно может закрыться прямо в `Initialize` (пустой список построек): тогда оно не показывается.

**Альтернативы.**

- *Колбэки (как было)* — работают, но переходы остаются в окнах, а ожидание — на флагах.
- *Generic-база `PopupPresenterBase<TResult>`* — компилятор проверял бы тип результата, но результат есть только у трёх окон из семи; свойство в окне проще.
- *Закрывать окно по крестику сразу, отдельным путём* — пропадает анимация, а ожидающий код никто не завершит.

**Последствия.**

- Из окон ушли `SceneSwitcherService` и `AbilitiesECSFactory`, из `PopupService` — `closedCallback` и `OnPopupCreated`.
- Сцена теперь переключается после анимации закрытия окна, а не одновременно с ней.
- Продолжение после `await` выполняется синхронно внутри `TrySetResult`, то есть в колбэке завершения твина DOTween.

## Фабрика состояний без контейнера (ADR)

**Статус:** принято, 28.10.2026.

**Контекст.** `GameplayStatesFactory` создаёт состояния геймплея (подготовка, волна, сбор лута, победа, поражение) и описывает переходы между ними. Конструктор принимает 17 зависимостей — всё, что нужно всем состояниям вместе. Обычное исключение из правила «контейнер никуда не передавать» — как раз фабрики: им нужно много зависимостей, и проще получить контейнер.

**Решение.** Оставить фабрику как есть: зависимости через конструктор, без `IObjectResolver` внутри и без разделения на несколько фабрик.

1. Фабрика делает одно дело — собирает граф состояний; длинный конструктор здесь честный список того, что нужно состояниям, а не признак лишней ответственности.
2. VContainer проверяет все зависимости фабрики при построении области сцены: незарегистрированный сервис роняет сцену сразу на старте.
3. Контейнер (`IObjectResolver`) по-прежнему видят только методы `Create...` в `*ScopeInstaller` — место сборки зависимостей.

**Альтернативы.**

- *Фабрика получает `IObjectResolver`, состояния регистрируются как `Transient`, создание — `_resolver.Resolve<WinState>()`.* Конструктор фабрики сокращается до одного параметра, а зависимости остаются видны в конструкторах состояний. Цена — пять регистраций и класс с контейнером внутри. В отличие от самописного контейнера, где фабрика вытягивала бы каждую зависимость руками, с фреймворком это допустимый приём (в Zenject — `DiContainer.Instantiate<T>()`, который создаёт и незарегистрированный класс; в VContainer `Instantiate` есть только для префабов, поэтому обычный класс нужно сначала зарегистрировать), но выигрыш — только в строках.
- *Разделить на несколько фабрик* (например, конечные состояния отдельно от игрового цикла) — меньше параметров в каждой, но граф переходов всё равно собирается в одном месте, и фабрики пришлось бы снова связывать между собой.

**Последствия.**

- Новое состояние — новые параметры конструктора фабрики. Пересмотреть решение, если состояний станет заметно больше (после пауз и настроек на этапе 2.4).
- Взрыв по клику вместе с `PointClickExplosionService` удалён при уборке после шага 2.3 (05.11.2026).

## Отладочный запуск (ADR)

**Статус:** принято, 05.11.2026.

**Контекст.** Чтобы проверить механику на 5-м уровне или урон новой способности, приходилось проходить игру до нужного места. Нужен запуск сразу в нужное состояние (уровень, волна, деньги, статы, способности) и читы в бою — для пользователя из окна редактора и для Claude командами Unity CLI. Настоящее сохранение при этом трогать нельзя, а в релизную сборку отладка попадать не должна.

**Решение.** Про отладку знает только точка сборки (composition root); игровые классы получают обычные параметры и стратегии.

1. **Передача настроек.** Окно редактора `Tools/Debug Launch` (сборка `RoguelikeTD.Editor`) пишет `DebugLaunchRequest` в `SessionState` и запускает Play Mode. `LaunchSettingsReader` при старте читает и стирает запрос (под `#if UNITY_EDITOR`); в сборке и при обычном запуске — `LaunchSettings.Normal` (Null Object, без `null`).
2. **Точка входа.** `GameEntryPoint` регистрирует `LaunchSettings` в контейнере: от них зависит папка сохранений (`Saves/Debug` вместо `Saves`) и стартовая сцена (сразу `Gameplay` вместо меню).
3. **Параметры боя — обычные аргументы сцены.** `GameplayInputArgs` получил стартовую волну, флаг «волны включены» и режим выбора способности. `StageProviderService` принимает номер стартовой волны, `PreparationState` — флаг волн. Это настройки уровня, а не «отладка», поэтому классы о ней не знают.
4. **Выбор способности — стратегия.** `IAbilitySelector` с реализациями `PopupAbilitySelector` (игра), `RandomAbilitySelector`, `SkipAbilitySelector`; нужную регистрирует `GameplayScopeInstaller` по аргументам сцены.
5. **Читы — только в сборке редактора.** Бессмертие, спавн, выдача способностей, уровень героя, манекен работают через существующие сервисы и компоненты (`EnemiesFactory`, `DropAbilityOnMainHeroLevelUpService.Provide`, `TakeDamageEvent`) из `DebugSession`. Команды CLI: `debug_start`, `debug_action`, `debug_state`.

**Альтернативы.**

- *Статический флаг `DebugLaunchSettings.Current` и проверки в игровых классах* — меньше кода, но скрытая зависимость (Service Locator против принятого внедрения через конструктор), игровые классы меняются из-за отладки (SRP/OCP), статику нельзя подменить в тесте.
- *Подмена каждого сервиса отладочной версией в контейнере* — ни одной проверки в коде, но интерфейсы и наследование ради отладки там, где хватает параметра.
- *Консоль разработчика внутри игры* — нужна для тестов в сборке; отложена (`Идеи.md`).

**Последствия.**

- Отладочные клавиши F и S убраны из бутстрапов сцен — теперь это кнопки окна; в релиз отладка не попадает.
- Манекен собран из варвара: без «мозга» он стоит, урон по нему восстанавливается, взрыв отключён (цель — он сам, радиус взрыва −1).
- «Выиграть сразу» нет: победа требует пройти все волны. Быстрый путь — старт с последней волны и «Убивать врагов сразу».
- Ускорение времени сбрасывается в ×1 при любой паузе (окно способности, конец боя): пауза пока один флаг (`TimeScalePauseService`).
