# Архитектура

## Сохранения

Данные игрока — `PlayerData` (`Runtime/Infrastructure/Data`). Сервисы читают и пишут свою часть через `IDataReader<PlayerData>` / `IDataWriter<PlayerData>`, регистрируясь в `PlayerDataProvider`. Сериализация — Newtonsoft.Json (`Core/DataManagement/Serializers/JsonSerializer.cs`).

### Совместимость со старыми сохранениями

Файл, сохранённый старой версией игры, может не содержать новых полей или новых ключей. Это решается в двух местах:

1. **Значение по умолчанию — в объявлении поля `PlayerData`.** Newtonsoft создаёт объект конструктором и заполняет только те поля, что есть в JSON; отсутствующие сохраняют значение из объявления.
2. **Недостающие ключи словарей — в `PlayerDataProvider.FillMissingData`.** После загрузки `DataProvider.LoadAsync` передаёт туда загруженные данные и стартовые (`GetOriginData()`, те же, что для новой игры). `AddMissingKeys` добавляет только отсутствующие ключи, сохранённые значения не трогает.

Что делать при добавлении данных:

| Что добавляешь | Что делать |
|---|---|
| Новое значение в существующий enum (валюта, стат) | Ничего — `AddMissingKeys` подтянет ключ из стартовых данных |
| Новый словарь, где у каждого ключа есть стартовое значение | Поле с `= new()` + строка `AddMissingKeys(loadedData.X, originData.X)` в `FillMissingData` + заполнение в `GetOriginData` |
| Новая коллекция, пустая на старте | Только `= new()` в объявлении поля |
| Новое число или флаг с нестандартным стартом | Значение прямо в объявлении: `public int Energy = 5;` — не через `FillMissingData`: после загрузки не отличить «поля не было» от «сохранён 0» |

Тест `PlayerDataProviderTests.Deserialize_EmptyJson_HasNoNullFields` проверяет, что ни одно ссылочное поле `PlayerData` не остаётся `null` после загрузки пустого `{}` — ловит поле, объявленное без `= new()`.

**Ограничение: список с непустым стартовым значением** (например, «на старте открыт герой 1»). Писать `= new() { 1 }` нельзя: Newtonsoft по умолчанию (`ObjectCreationHandling.Auto`) дописывает элементы из файла в существующий список, и сохранённое `[1, 2]` загрузится как `[1, 1, 2]`. Когда такой список понадобится — включить `ObjectCreationHandling.Replace` в `JsonSerializer` (коллекция из файла заменяет значение из объявления; если поля в файле нет — остаётся стартовое).

**Когда вводить версию сохранения и миграции:** при ломающих изменениях формата — переименование или перенос поля, смена смысла значения. Дополнение недостающих данных этого не требует.

## Статы героя и модификаторы

Компоненты сущности (`Gameplay/Features/StatsFeature`):

- `BaseStats` — значения из прокачки (`StatsUpgradeService`), в бою не меняются;
- `StatsEffects` — список модификаторов `IStatsEffect` (`StatsEffect`: стат + функция `float → float`);
- `ModifiesStats` — итоговые значения, их читают системы-синхронизаторы (`…StatSynchronizerSystem`) и переносят в `Damage`, `MaxHealth` и т. д.

`StatEffectsApplierSystem` при каждом добавлении или удалении эффекта пересчитывает итог с нуля: копирует `BaseStats` в `ModifiesStats` и по очереди применяет все эффекты.

**Правило: стат в бою меняется только добавлением эффекта в `StatsEffects`.** Прямая запись в `ModifiesStats` стирается при следующем пересчёте. Так терялся купленный буст урона (`IncreaseDamageAbilitySystem`) после подбора любой способности на статы — исправлено, покрыто тестом `StatEffectsApplierTests.AddEffect_AfterIncreaseDamageBoost_KeepsBoost`.

**Порядок эффектов влияет на итог.** Эффекты применяются в порядке добавления: `+5`, затем `×2` даёт `(10 + 5) × 2 = 30`, в обратном порядке — `10 × 2 + 5 = 25`. Сейчас все способности на урон — умножение (от порядка не зависит). Если появятся сложения вместе с умножениями и порядок станет проблемой — применять эффекты по фиксированным стадиям (сначала сложение, потом умножение).

## Реактивность

Своя реализация (`Core/Reactive`): `ReactiveVariable<T>` (уведомляет `(старое, новое)` при изменении `Value`), `ReactiveEvent<T>` / `ReactiveEvent`. Подписчики хранятся в общем `SubscribersList<T>`.

- Подписка и отписка внутри обработчика применяются со следующего уведомления (как у C# `event`): они ставятся в очередь, очередь разбирает только самый внешний вызов.
- **Вложенный вызов безопасен.** Обработчик может снова изменить ту же переменную или вызвать то же событие (так делает `LevelUpSystem`: в обработчике опыта записывает остаток обратно в опыт). Раньше это падало с `Collection was modified`, если в этот момент кто-то подписывался или отписывался; исправлено счётчиком вложенности, покрыто тестами `…FromHandlerWhileSubscriptionPending_DoesNotThrow`.
- **Правило для подписчиков:** при вложенных изменениях уведомления приходят не по порядку (сначала вложенное `120 → 20`, потом внешнее `0 → 120`). Если переменную могут менять из обработчиков, читай текущее `Value`, а не аргумент `newValue` (так делает `MainHeroExperiencePresenter`).
- `Subscribe` не присылает текущее значение (в отличие от `ReactiveProperty` в R3) — начальное состояние читать через `Value` при подписке.

## DI: VContainer (ADR)

**Статус:** принято, 26.10.2026.

**Контекст.** Был самописный контейнер (`Core/DI`): регистрация фабричными методами, дочерний контейнер на сцену, `IInitializable`/`IDisposable`. Фабрики и презентеры получали сам контейнер и вызывали `Resolve` внутри (service locator: 205 вызовов в 20 файлах). При разборе нашлись баги жизненного цикла:

1. Ленивый сервис, впервые запрошенный после `Initialize()`, не получал `IInitializable.Initialize()`.
2. `Initialize()` проходил по регистрациям один раз: если `NonLazy`-сервис при создании запрашивал ленивый, стоящий раньше в списке, тот создавался после прохода и тоже не инициализировался.

**Решение.** Перейти на VContainer 1.19.0.

1. Сначала убрать service locator на старом контейнере: зависимости — через конструктор, контейнер видит только корень композиции (`*ContextRegistrations`, `*Bootstrap`, `GameEntryPoint`). После этого замена контейнера свелась к регистрациям.
2. Области создаются **из кода**: корневая — `LifetimeScope.Create` в `GameEntryPoint` (`DontDestroyOnLoad`), сцены — `CreateChild` в `SceneSwitcherService`. Сцены и префабы не меняются.
3. Регистрации — автосвязывание (`builder.Register<T>(Lifetime.Singleton)`); лямбды — только для конфигов (читаются при первом запросе, после загрузки), префабов (`Instantiate`) и аргументов сцены (`RegisterInstance`).
4. Сервисы с `Initialize` — точки входа (`RegisterEntryPoint().AsSelf()`): VContainer создаёт их при построении области и вызывает `Initialize` по порядку регистрации. VContainer вызывает `Initialize` **только у точек входа** — сервис с `IInitializable`, зарегистрированный обычным `Register`, его не получит.
5. Сервисы, которые должны существовать до загрузки сохранения (сами регистрируются в `PlayerDataProvider` в конструкторе), создаются заранее через `RegisterBuildCallback`.

**Альтернативы.**

- *Zenject (Extenject)* — тот же функционал, но проект не развивается с 2022 года, медленнее, больше аллокаций, огромный API.
- *Починить свой контейнер* — два найденных бага чинятся, но это поддержка велосипеда без выигрыша; диагностика, производительность и знакомость для команды — у готового решения.
- *Области через компонент `LifetimeScope` на сцене* — стандартный способ, но требует правки сцен и смены схемы загрузки; создание из кода сохранило существующий поток `SceneSwitcherService`.

**Последствия.**

- Зависимости видны в конструкторах; классы создаются в тестах без контейнера. Большие конструкторы (`GameplayStatesFactory` — 17 параметров) стали заметны — кандидаты на разделение.
- `LifetimeScope` — `MonoBehaviour` и освобождает сервисы в `OnDestroy`. При выходе из игры Unity уничтожает объекты в произвольном порядке, поэтому `SceneSwitcherService` освобождает область сцены на `Application.quitting`, пока все объекты живы.
- Освобождение области вызывает `Dispose` у всех созданных `IDisposable`: сервисы, меняющие глобальное состояние, обязаны вернуть его в `Dispose` (пример — `TimeScalePauseService` снимает паузу).
- **Риск для WebGL/IL2CPP:** VContainer создаёт объекты через рефлексию по конструкторам; агрессивное вырезание кода (managed stripping) может удалить «неиспользуемые» конструкторы. Проверить на WebGL-сборке; решение — `link.xml` или source generator VContainer.
- Известная временная связность, оставленная как есть: сервисы-читатели сохранения регистрируются в `PlayerDataProvider` в своём конструкторе (отсюда `RegisterBuildCallback`).
